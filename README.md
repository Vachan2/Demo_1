# Sentinel Demo 1 — Autonomous SRE

A production-realistic demonstration of an AI SRE agent detecting, diagnosing,
patching, and verifying a database connection-leak incident end-to-end.

```
E-Commerce Order API  →  PostgreSQL (connection pool exhaustion)
        ↓
  Sentinel Detector   (metrics thresholds)
        ↓
  Context Builder     (metrics + deployment history + source code)
        ↓
  Agent RCA           (LLM or rule-based, confidence-ranked)
        ↓
  GitHub Tool         (branch + patch + PR)
        ↓
  Validator           (lint + unit + integration + leak regression)
        ↓
  Verification Engine (load test before vs after)
        ↓
  Incident RESOLVED
```

---

## Quick Start (5 minutes)

### 1. Start Postgres

```bash
make db
```

### 2. Start the Order API  *(new terminal)*

```bash
make order-api
```

### 3. Start Sentinel  *(new terminal)*

```bash
cd sentinel && cp .env.example .env   # optionally add OPENAI_API_KEY
make sentinel
```

### 4. Open the dashboard

```bash
make dashboard
# or open dashboard/index.html in any browser
```

## Demo Walk-through

### Stage 1 — Everything is healthy

```bash
curl http://localhost:9000/health
curl http://localhost:9000/orders/123
```

### Stage 2 — Introduce the production bug

```bash
make demo-failure
```

This activates `DEMO_FAILURE_MODE=connection_leak` at runtime — no restart needed.
The diff looks like a reasonable "optimisation":

```diff
-    async with pool.acquire() as conn:
+    conn = await pool.acquire()
+    try:
         return await conn.fetchrow(...)
+    except Exception:
+        raise
# Missing: await pool.release(conn)
```

### Stage 3 — Generate traffic

```bash
make load-gen
```

Watch the dashboard: error rate climbs, P95 latency spikes, pool hits 10/10.

### Stages 4–10 — Sentinel takes over

Sentinel detects the anomaly from pushed metrics, runs RCA, generates a patch
on a new branch, validates the patch, and verifies the fix against the same
workload.

To run the full interactive script:

```bash
make demo-run
```

## Configuration

| Variable | Default | Description |
|---|---|---|
| `OPENAI_API_KEY` | _(empty)_ | GPT-4o RCA. Falls back to rule-based if unset. |
| `GITHUB_TOKEN` | _(empty)_ | PR creation. Falls back to local git if unset. |
| `GITHUB_REPO` | _(empty)_ | `org/repo` for PR target. |
| `ERROR_RATE_THRESHOLD_PCT` | `5.0` | Incident trigger threshold. |
| `LATENCY_P95_THRESHOLD_MS` | `2000` | Incident trigger threshold. |
| `DB_POOL_UTILISATION_THRESHOLD_PCT` | `80` | Incident trigger threshold. |

## Tests

```bash
make test             # all tests
make test-unit        # unit tests (no DB required)
make test-integration # integration tests (needs Postgres)
make test-leak        # connection-leak regression only
```

The connection-leak regression test is the most important:

- `test_healthy_releases_connection` — verifies the fixed path releases connections
- `test_buggy_leaks_connection` — verifies the buggy path still leaks (keeps the demo honest)
- `test_concurrent_requests_do_not_exhaust_pool` — 20 concurrent calls against a pool of 10

## Sentinel API

| Endpoint | Description |
|---|---|
| `POST /api/v1/metrics` | Receive metrics from order-api (auto-detect) |
| `POST /api/v1/incidents` | Manually open an incident |
| `GET  /api/v1/incidents` | List all incidents |
| `GET  /api/v1/incidents/{id}` | Get a single incident |
| `POST /api/v1/incidents/{id}/investigate` | Trigger RCA only |
| `POST /api/v1/incidents/{id}/remediate` | Generate patch + PR |
| `POST /api/v1/incidents/{id}/validate` | Run test suite |
| `POST /api/v1/incidents/{id}/verify` | Run post-fix load test |
| `POST /api/v1/incidents/{id}/run` | Full pipeline end-to-end |
| `GET  /api/v1/status` | System status |

---

*This demo reproduces a realistic failure pattern (database connection pool
exhaustion) documented in production incident reports. It is a simulation
designed to demonstrate autonomous incident remediation, not a reproduction
of any specific company's outage.*
